# 《Music in English》文档审查报告

> 审查对象：《教学APP开发需求规格书 v2.0》《用英语学音乐课程设计方案 v2.0》
> 审查日期：2026-09-02 · 审查方法：逐条核对 + 外部事实核验 + 流程推演
> 分级体系：**严重**（开发前必须修复，否则阻塞或返工）/ **重要**（MVP 内应修复）/ **一般**（建议优化）

---

## 一、总体结论

两份文档整体质量高：需求分层清晰、AI 应用形式定案有调研依据、成本测算数量级可信、双模式部署考虑周全。经外部核验，**DeepSeek 模型选型（deepseek-v4-flash）与弃用时间线（2026-07-24）属实**，定价数量级（输入约 1 元/百万 token、输出约 2 元/百万）与文档一致。 [DeepSeek API Docs](https://api-docs.deepseek.com/updates/ "citation"), [TheRouter.ai](https://therouter.ai/news/deepseek-v4-api-migration-deprecation-2026/ "citation")

但存在 **5 项严重、8 项重要、6 项一般** 缺陷，其中"大陆网络环境下 Web Speech API 不可用""存储配额测算错误""数据模型缺 3 张表"必须在编码前修复。

## 二、严重缺陷（5 项）

### S-1 Web Speech API 作为主路径在中国大陆不可行
- **位置**：SRS FR-5.2、§8.2 ASR 选型。
- **问题**：Chrome 的 Web Speech 识别依赖 Google 云端服务，大陆网络环境下 Android Chrome 上基本不可用；目标用户为中国初中生，即主路径对大部分 Android 设备直接失效，只剩 iOS Safari（走 Apple 服务）可用。此外 Web Speech 会把音频发送到 Google/Apple 服务器，与文档"未成年人数据敏感、AI 调用日志脱敏"的合规立场存在张力。
- **修复建议**：ASR 路径改为**按设备/网络探测分流**——默认走云端 Whisper 兼容服务（上传已录制的音频，与 MediaRecorder 天然衔接）；仅当探测到 iOS Safari 且用户开启"本地识别"时启用 Web Speech 实时预览。文档中"MVP 用 Web Speech，失败降级 Whisper"应反转为"**Whisper 兼容服务为主，Web Speech 为增强预览**"。成本侧：Whisper 兼容服务按量付费，需在 §8.10 补一行测算（20 生 × 320 次 × 平均 60 秒，按常见 0.006 元/秒级报价估算约 110 元量级，仍在 300 元预算内，但需实测确认）。
- **另一个技术事实**：Web Speech 的识别流**无法回放已录制的音频文件**——它只识别实时麦克风流。因此"录音 + 事后转写"的架构本来就必须把音频送到服务端，文档 §8.7 的链路 [2] 描述需要按此修正。

### S-2 存储配额测算错误，稳态必然超 1GB
- **位置**：SRS §8.9、§4 存储非功能需求。
- **问题**：文档估算"稳态 < 800MB"，但按自身参数推演：锚点录像 ≤25MB/条、30 天滚动保留。课程 8 周 56 天，30 天窗口内每生约有 4 个单元的锚点录像在架（FR-7.3 只保留最终确认版，按 4 条计）：20 生 × 4 条 × 25MB ≈ **2GB**，加上毕业作品 20 × 40MB = 800MB，合计约 2.8GB，**超出免费层 1GB 近 3 倍**。
- **修复建议**（任选其一或组合，需写回 SRS）：
  1. 锚点录像保留期从 30 天缩短为 **14 天**（窗口内约 2 条/生 → 20 × 2 × 25MB = 1GB，仍紧）；
  2. 录像码率从 1.2Mbps 降到 **700Kbps + 540p**（3 分钟 ≈ 16MB/条），配合 14 天保留 → 约 640MB + 毕业作品压缩至 ≤25MB（500MB）≈ 1.1GB，边缘可行；
  3. **最稳妥**：把 §8.9 提到的 local-fs StorageAdapter 从二期提前到 W7，本地部署模式下录像直写磁盘，云端仅试用生使用——试用规模控制在 10 生以内时云端方案 2 可行。
- 同时建议：上传前在浏览器端做一次压缩/降码率（MediaRecorder bitrate 参数 + 必要时 canvas 转码），并在管理端加"配额 80% 告警"的具体实现任务（文档只提了告警，未列入排期任何一周）。

### S-3 数据模型缺 3 张关键表
- **位置**：SRS §8.8。
- **问题**：
  1. **缺 `lesson_progress` 表**：FR-2.4 断点续学（P1）需要持久化"关卡内步骤 / 视频播放位置 / 已完成清单项"，现有表无法承载；
  2. **缺 `coach_sessions` / `coach_messages` 表**：FR-5.5 陪练对话（U6）的会话与轮次记录无落库位置，"≤10 轮限制"和质量抽检都无从实现；
  3. **缺 `feedback_votes` 表**：§6.6 统一规范要求"这条反馈有用吗 👍/👎"进质量看板，但无对应表。
- **修复建议**：补三张表（字段建议见《代码示例.md》§9），并将 `anchor_submissions.unit_no` 改为 `lesson_id` 外键，与 speaking/writing 两表对齐（当前混用 unit_no 和 lesson_id，层级不一致）。

### S-4 监护人确认只有勾选框，合规闭环不完整
- **位置**：SRS FR-1.1、§4 隐私合规。
- **问题**：面向 12–15 岁用户，其中 12–13 岁属于"不满 14 周岁未成年人"，依《个人信息保护法》需取得**父母或其他监护人的同意**。"注册需监护人确认勾选"由学生自己点一下即可完成，不构成有效的监护人同意链路；也无监护人联系方式、撤回同意、查看/删除孩子数据的入口。
- **修复建议**：MVP 范围内最小合规闭环——① 注册时填写监护人手机号/邮箱，系统发送确认链接，**监护人点击确认后账号才激活学习功能**（激活前只能浏览课程地图）；② 个人主页提供"监护人入口"（查看作品集、一键导出、申请删除账号）；③ 账号删除流程在 SRS 补一条功能需求（当前只在非功能需求提了一句"留删除入口"）。此事建议立项时做一次法务咨询，文档中明确记录结论。

### S-5 AI 用量限额与验收标准、陪练功能互相冲突
- **位置**：SRS §5.3 [2]（每生每日 ≤3 次）、§10 验收标准 3（连续 20 次提交无格式崩坏）、FR-5.5（陪练 ≤10 轮）。
- **问题**：① 验收测试无法在普通账号下完成（第 4 次就被限额拦住），文档未说明测试/管理员豁免通道；② 陪练对话是否计入 3 次限额未定义——10 轮对话若每轮都算一次调用，一次陪练就耗尽 3 天配额；③ 系统自动重试（§5.3 [4]）是否消耗学生配额未定义，若消耗则学生会莫名被限。
- **修复建议**：明确三类口径并写回 SRS——① 限额只计**学生主动触发**的反馈调用，系统重试不计；② 陪练按"会话"计 1 次（而非按轮），或单独设每生每周 2 次陪练额度；③ 增加 `role=admin/test` 账号豁免限额，验收测试用测试账号执行。

## 三、重要缺陷（8 项）

### I-1 DeepSeek v4-flash 默认开启思考模式，需显式关闭
- **外部核验事实**：V4 系列**默认 thinking mode 开启**，仅改模型名不显式传 `thinking: {"type":"disabled"}` 会导致响应延迟和 token 消耗悄然上升，直接冲击"AI 反馈 < 10s"和成本测算。 [TheRouter.ai](https://therouter.ai/news/deepseek-v4-api-migration-deprecation-2026/ "citation")
- SRS §8.2 写了"思考模式关闭"但 §8.5/§8.6 没有落到参数层面。**修复**：在《代码示例.md》§1 的 provider 封装中固化为默认参数，并在 project_rules.md 中列为强制约束。

### I-2 Supabase 安全策略（RLS / 签名 URL）全文缺失
- §8.8 只有表结构没有行级安全策略。学生媒体若用公开 URL 即可被遍历访问，属于未成年人音视频泄露事故级风险。**修复**：所有表启用 RLS（`auth.uid() = user_id`），Storage 桶私有 + 短期签名 URL（≤15 分钟）；分享链接走独立的 `share_tokens` 表（不可猜测 token + 只读视图），不要直接公开 Storage 路径。策略示例见《代码示例.md》§9。

### I-3 iOS MediaRecorder 容器格式坑未提
- iOS Safari 的 MediaRecorder 产出 `audio/mp4` / `video/mp4`，Chrome 产出 `webm`。若前端硬编码 webm，iOS 上录音直接失败（验收标准 5 会挂）；上传与播放链路也要按 mimeType 分流。**修复**：录制组件做 `MediaRecorder.isTypeSupported` 探测（示例见《代码示例.md》§5），数据库 `audio_path/video_path` 旁存 `mime_type` 字段。

### I-4 视频失效检测的实现路径未定
- FR-3.6 说"定期检测"但未定义手段。可行路径：YouTube **oEmbed 端点**（无配额、可探下架/禁嵌，但探不了区域屏蔽）+ iframe API 的 `onError`（码 101/150 = 禁止嵌入）前端上报。**修复**：双通道——管理端 cron 走 oEmbed 日检 + 学生端播放错误实时上报 `videos.status`；Vercel Hobby cron 每日一次够用，写入排期 W7。

### I-5 内容灌装 CSV 的幂等与校验规则未定
- §9 W7 交付"CSV 导入 + 字幕导入脚本"，但无主键冲突策略。重跑导入若产生重复词块/视频，学生端复习队列会出错。**修复**：所有导入以 `(unit_no, item_no)` 或 `youtube_id` 为幂等键做 upsert；导入前跑 Zod 校验（与 lib/ai 的 schema 复用同一套），失败行报告行号与原因。示例见《代码示例.md》§8。

### I-6 AI 质量"历史样本回归"与"日志脱敏"存在实现矛盾
- §5.5 [4] 要求"新模板对历史样本重放"，§8.5 logger 又规定"不存学生原文"。重放需要输入文本。**修复**：明确分工——`ai_call_logs` 只存元数据 + `submission_id` 引用；重放时按 id 回 `speaking_submissions/writing_submissions` 取原文。这不违反脱敏原则（日志本身脱敏），但文档需要写明，否则开发时会被误实现为"日志存原文"或"重放不可用"。

### I-7 关卡完成判据未定义，pending 状态与解锁的关系模糊
- §5.2 状态机只有"未解锁→进行中→已完成"，但每关"什么算完成"没有形式化定义：L4 口语在 AI 反馈 pending 时算不算完成？（按 §4 可靠性"不阻塞"应为算完成，但没写死。）L3 锚点录像未上传能否进 L4？**修复**：为 L1–L6 各定义完成判据清单（见《流程图与推演.md》§2），核心规则：**AI 反馈 pending 不阻塞关卡完成，只阻塞"入档"**。

### I-8 成长曲线"写作错误率"无计算口径
- FR-8.2 要画"错误率趋势"，但 AI 批改返回的错误条数除以什么（词数？句数？）未定义，口径不定曲线就是噪声。**修复**：定义为 `必改错误数 / 总词数 × 100`，写入 `writing_submissions.review_json.stats`，前端只读不算。

## 四、一般缺陷（6 项）

| 编号 | 位置 | 问题 | 建议 |
|---|---|---|---|
| G-1 | §7 UI 规范 | 无深色模式策略 | MVP 明确"仅浅色"，避免开发中顺手做一半 |

## 五、AI Agent 方案可行性复核

**结论：可行，且是约束条件下的最优解。** 逐项复核：

| 维度 | 复核结论 |
|---|---|
| 模型选型 | ✅ deepseek-v4-flash 真实存在、定价与文档一致、1M 上下文远超需求（单任务 prompt < 3K token）；旧名已如期弃用，文档时间线正确。 [DeepSeek API Docs](https://api-docs.deepseek.com/updates/ "citation") |
| 结构化输出 | ✅ Vercel AI SDK `generateObject` + Zod 是该栈标准做法；JSON 失败率 < 2% 的目标在"重试 1 次 + temperature=0"策略下合理可达 |
| 延迟目标 | ⚠️ 有条件成立：< 10s 必须显式关闭 thinking 模式（见 I-1）；陪练流式首 token 通常 < 3s，达标 |
| 成本 | ✅ 8.10 测算数量级可信（约 6 元/20 生/8 周），但需补上 Whisper 降级与内容预生成的实测复核（见 S-1） |
| 未成年人护栏 | ⚠️ 方向正确但需补强：guard.ts 的"敏感词扫描"建议改为**双层**——关键词表（快、确定）+ LLM 二审仅对陪练自由文本触发；陪练 system prompt 需明确"不索取个人信息、不讨论非音乐话题、遇越界固定话术转向" |
| 质量运营 | ✅ Prompt 版本化 + 周抽检 + 历史回归是成熟的轻量 eval 实践；建议 MVP 即建立 20 条 golden 样本集（口语/写作各 10），每次模板变更必跑 |

**不建议变更架构，仅需按 S-1/S-5/I-1/I-6 修订。**

## 六、GitHub 可用开发基础调研

**结论：没有完全对口的"课程闯关 + 媒体采集"成品项目，但有 2 个官方/半官方模板可覆盖 60% 以上底座代码，推荐组合使用。**

| 项目 | 覆盖内容 | 与本项目差距 | 建议用法 |
|---|---|---|---|
| **vercel/ai-chatbot**（官方，约 20k★） | Next.js App Router + TS + Vercel AI SDK + shadcn/ui + Tailwind + Postgres + Auth + 流式对话 + 结构化输出范式 | 用 Neon/Auth.js 而非 Supabase；无课程/关卡/媒体采集概念 | **AI 编排层与流式 UI 的参考实现**，lib/ai 各文件照其模式组织 |
| **Supabase Vercel AI Chatbot**（约 800★，Vercel Labs + Supabase 成员移植） | 同上，但 **Auth 与 DB 已换成 Supabase** | 项目更新频率低，需核对依赖版本 | **推荐作为脚手架起点**：fork 后删除聊天业务页，保留 auth + DB + AI SDK 管线，在其上加课程域 |
| vercel/next.js 的 `with-supabase` 示例 | 最小 Supabase Auth + SSR 接线 | 无 AI 部分 | 若担心上一个项目陈旧，用此打底 + 手工接入 AI SDK（多约 2 天工作量） |
| Vercel AI SDK 官方 examples | `generateObject` / `streamText` / tool calling 的最小范例 | 单点示例非完整应用 | 开发 L4/L5/U6 时对照查阅 |

配套零散库（均有维护、可直接用，不必自研）：

| 能力 | 库 | 备注 |
|---|---|---|
| YouTube iframe 控制 | `react-youtube`（官方 API 的 React 封装） | start/end 切片、onStateChange、onError（禁嵌检测） |
| SM-2 间隔重复 | `ts-supermemo` | 三档自评映射 grade 即可，无需自写算法 |
| 图表 | Recharts（SRS 已选） | 热力图需自绘格子或用 `cal-heatmap` |
| 图标 | lucide-react（SRS 已选） | — |
| 录音录像 | 原生 MediaRecorder + 自写 hook | 不建议引 recordrtc（重且维护放缓），示例见《代码示例.md》§5 |

**落地建议**：以 Supabase Vercel AI Chatbot 为起点，可省约 W1 整周脚手架工作；但**不要把它的聊天页当业务基础改**——课程域模型差异大，删干净再建比自己改更快。
